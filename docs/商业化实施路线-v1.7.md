## 一、产品定位

**一句话**：一个**完全在本地运行**的地理围栏打卡提醒工具 —— 到点自动提醒、离开自动留痕、事后可修可导出。

| 维度 | 界定 |
| --- | --- |
| 目标用户 | 通勤制上班族、外勤/巡店/驻场人员、需要按地点证明「我到了」的自由职业者 |
| 使用场景 | 忘记打卡、迟到早退有争议、多地点轮转、需要导出记录交给 HR 或客户 |
| 核心价值 | **不丢数据 + 不误判 + 不耗电 + 不上传** |
| 明确边界 | 不做考勤审批、不做团队管理、不做路线导航、不做云同步 |

**为什么不做考勤闭环**：一旦引入审批与团队，就要承担企业数据受托责任、等保与劳动合同合规成本，而这些能力与「个人提醒工具」的用户预期无关。**把个人侧做到极致、把数据主权完整交给用户**，才是不需要资质护城河也能立足的位置。

## 三、差异化亮点

同类产品（牛马时录、出勤记录、上班打卡日历、Tasks.org 等）在功能清单上高度趋同。我们**不在功能数量上竞争**，而是守住四条别人难以同时满足的线：

| # | 差异化 | 为什么别人难跟上 |
| --- | --- | --- |
| **D1** | **自适应调频的围栏**：全部远离时 30 秒一次，接近或已进入时 5 秒一次 | 同类普遍用固定间隔（10 分钟~1 分钟）。固定间隔要么费电、要么迟钝，**只能二选一**；我们靠 `FenceStateMachine` 的状态分层同时拿到两端 |
| **D2** | **开关式隐私模型**：`allowBackup=false` + 无网络上传 + 用户显式导出 | 多数产品为了「换机不丢」默认走云同步，位置数据必然离开设备。我们反过来：**放弃自动备份，换取数据不出本机**，再用导入导出补上可迁移性 |
| **D3** | **可解释性**：10 项保活自检 + 定位调试页 + 鉴权失败直读原始上报值 | 国产 ROM 保活失败时，竞品通常只表现为「没提醒」，用户无法自查。我们把内部状态（定位来源、精度、回调间隔、围栏状态、权限、电池优化、ROM 策略）全部暴露可读 |
| **D4** | **数据可携带且可校验**：CSV（UTF-8 BOM）+ 带 `schemaVersion` 的 JSON 备份 | 导出看似简单，但要同时做到「Excel 不乱码」「点名叫『公司,总部』不串列」「版本升级后旧备份仍可恢复」，需要格式治理而非一次 `joinToString` |

> **D2 与 D4 是一组**：先用 D4 把「不云同步」的代价补平，D2 才敢作为卖点对外讲。

## 四、非功能要求

### 4.1 可扩展性

| 机制 | 现状 |
| --- | --- |
| **分层清晰** | data（Room）/ repository / geofence / stats / backup / ui，单向依赖，无循环 |
| **纯逻辑与框架解耦** | `StatsCalculator`、`MonthCalendarModel`、`CsvExporter`、`BackupCodec`、`FenceStateMachine`、`LocationIntervalScheduler` 全是**无 Android 依赖的纯 Kotlin**，可被 JVM 单测完整覆盖 |
| **版本化格式** | 备份带 `schemaVersion`，高版本备份**拒绝恢复**而非猜测解析；数据库用 `@AutoMigration` 显式声明升级路径 |
| **文案资源化** | data 层不承载中文；所有用户可见文案集中在 `strings.xml`，为多语言预留 |
| **依赖收敛** | 图表自绘（Canvas）、JSON 自实现、DB 用 Room 自带的 KSP；“每一项新依赖都要能说清它挡掉了多少行代码” |

### 4.2 稳定性

| 机制 | 现状 |
| --- | --- |
| 前台服务 + `ServiceWatchdog` + 开机自启 | ✅ |
| 唤醒锁心跳续期（`PARTIAL_WAKE_LOCK` 按时长续租） | ✅ |
| 围栏状态机单次写回 + 主线程队列尾投递调频 | ✅ |
| **失败不静默**：定位失败、鉴权失败、恢复失败都给出可读原因 | ✅ |
| **不可逆操作一律二次确认**（清空记录、覆盖恢复） | ✅ v1.7.0 |
| 进程级单例一致性（`PreferencesStore.get()`） | ✅ |

### 4.3 数据安全

| 项 | 措施 | 备注 |
| --- | --- | --- |
| 签名密钥 | `keystore.properties` 不入库；读取优先级 **环境变量 > Gradle 属性 > 本地文件** | CI 可不落盘 |
| 系统备份 | `allowBackup=false`（v1.6.0 起），位置与记录不进入系统云备份 | |
| 存储位置 | 应用私有目录，其他应用不可读 | |
| 导出文件 | 走 SAF，用户显式选择落点；**导出内容含位置，需在 UI 明确告知** | 见第七节 T7 |
| 日志 | 只打印错误码与状态，**不打印坐标** | |
| 数据库加密（SQLCipher） | **暂不引入** | 理由：Android 10+ 已默认文件级加密（FBE），再加一层会显著增加体积与启动耗时，且需自管密钥 —— 对当前威胁模型收益不足。若将来面向企业客户再评估 |

### 6.2 合规与稳定性加固

- 新增**完整隐私政策页**（设置 → 关于 → 隐私政策），覆盖收集范围、使用方式、存储位置、第三方 SDK、权限说明、用户权利、未成年人、政策更新共八节。
- 清理 `PermissionCard` 中残留的 **`@Composable` 提前返回** —— 这是 v1.6.0 已导致真机闪退的同一类缺陷（Compose 编译器生成多余 `endReplaceableGroup`，release 下 group 失配抛 `ArrayIndexOutOfBoundsException`）。现已约定 UI 层一律不使用提前返回，并在代码中留注释说明原因。
- 版本号 `1.6.0 / versionCode 2` → **`1.7.0 / versionCode 3`**。

### 6.3 架构调整（为可扩展性）

把记录相关职责从 `MainViewModel` 拆出为独立的 **`RecordsViewModel`**：记录、统计、导出、备份、编辑状态各自独立订阅，`MainViewModel` 回归「打卡点 + 保活监控」。这正是原审计报告 D5-3 建议的方向 —— 本次因新增统计与导出而**必须**拆分，否则单个 ViewModel 会同时承担 12 个以上数据源。

新增包结构：

```
com.example.checkin
├── stats/          StatsModels · StatsCalculator · MonthCalendarModel   （纯 Kotlin）
├── backup/         Json · CsvExporter · BackupCodec                     （纯 Kotlin）
└── ui/records/     RecordsViewModel · RecordsScreen · CalendarSection
                    · StatsSection · RecordEditDialog · ClearRecordsDialog
```

### 8.2 真机回归清单（本批次需验）

1. 记录页侧滑删除 → 出现「撤销」→ 点击后记录**按原 id 与原时间**回到列表；
2. 撤销窗口超时后再次删除 → 只能撤销最后一次；
3. 点顶栏清空 → 弹出确认框并显示条数；取消不产生任何写库；
4. 编辑一条记录的时间与备注 → 回列表可见备注，时间已更新；
5. 跨零点的记录（进出跨午夜）→ 日历两天各有色块，统计口径不重复计；
6. 日历点击某天 → 下方明细联动；
7. 统计切日/周/月 → 数字与日历一致，柱状图随区间变化；
8. 导出 CSV → 用 Excel/WPS 打开**中文不乱码**、列对齐正确；
9. 导出 JSON 备份 → 清空应用数据后从备份恢复 → 打卡点与记录完整回来，且**监控能立即重新生效**；
10. 设置 → 关于 → 隐私政策 → 可完整阅读并返回；
11. 权限齐全时首页不显示权限提示卡（验证 `PermissionCard` 提前返回改造无副作用）。
