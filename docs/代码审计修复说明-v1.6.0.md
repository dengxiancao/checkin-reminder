1. **`unitTests.isReturnDefaultValues` 保留 `true`**

## 五、真机联调补充修复（2026-10-13）

用户反馈「定位无响应 + 点定位调试页闪退」。真机（小米 11 / Android 13 / arm64-v8a）联调后**两个问题都定位到根因并已修复**。

### C6（P0）定位调试页必崩 — 已修【新增】

**现象**：设置页 → 「打开定位调试页」→ 进程立即退出。100% 复现。

**崩溃堆栈**（release 混淆包，用 `mapping.txt` 反混淆）：

```
FATAL EXCEPTION: main
java.lang.ArrayIndexOutOfBoundsException: length=0; index=-5
	at androidx.compose.runtime.ComposerImpl.end           // h0.r.t
	at androidx.compose.runtime.ComposerImpl.doCompose     // h0.r.r
	at androidx.compose.ui.layout.LayoutNodeSubcompositionsState
	at androidx.compose.material3.ScaffoldKt$LegacyScaffoldLayout$1$1
	at androidx.compose.ui.platform.AndroidComposeView.onMeasure
```

**根因**：`@Composable` 内的**提前返回**（裸 `return` / `return@Column` 这类限定返回）会让 Compose 编译器生成**多余的 `endReplaceableGroup()`**，造成 group start/end 不平衡。debug 构建下被掩盖，**release（R8 优化后）暴露为 `ArrayIndexOutOfBoundsException: length=0; index=-5`**。
这是上游已确认的缺陷（JetBrains compose-jb issue **#2225 / #2230**，StackOverflow 75573483），其官方案例堆栈与本项目**逐帧吻合**。

**修复**：全工程「@Composable 内的提前返回」改写为标准 `if / else if / else`：

| 文件 | 原写法 | 改法 |
| --- | --- | --- |
| `ui/debug/DebugScreen.kt` | `DebugPermissionCard` 内裸 `return` | 拆出独立 `@Composable PermissionGuideCard` |
| `ui/debug/DebugScreen.kt` | `CurrentLocationCard` 内 `return@Column` | 拆出独立 `@Composable LocationDetailRows` |
| `ui/screen/RecordsScreen.kt` | `return@Scaffold` | `if (空) { Box } else { LazyColumn }` |
| `ui/confirm/CheckinConfirmScreen.kt` | 3 处 `return@Column` | 合并为单条 `if / else if / else` |

> 「打卡记录」页在**记录为空**时走的正是 `return@Scaffold` 分支，**同样会崩**，一并修好了。

**复查**：全工程其余 `return@launch / @post / @Runnable / @SideEffect / @DisposableEffect / @LaunchedEffect / @AndroidView（update 回调）/ @locate（onClick）` 均位于**非 @Composable 上下文**，安全，未改动。

**真机验证（修复前 → 修复后）**：

| 页面 | 修复前 | 修复后 |
| --- | --- | --- |
| 设置 → 打开定位调试页 | 必崩 | ✅ 正常打开，crash buffer 为空 |
| 打卡记录页（空列表） | 同样会崩 | ✅ 正常显示「暂无打卡记录」 |
| 打卡点页 / 设置页 | 正常 | ✅ 正常 |

### C7（P2）鉴权失败被显示成「未知错误」— 已修【新增】

真机实测发现：**签名 SHA1 与控制台登记不一致时，高德新版定位 SDK 不返回 26，而是返回 `code=8`**，
真正线索藏在 `errorInfo` 中：

```
auth fail:INVALID_USER_SCODE#SHA1AndPackage#0F:65:D5:1D:...:27:0C:13:com.example.checkin
json: {"info":"INVALID_USER_SCODE","infocode":"10008","status":"0"}
```

原实现只按错误码 8 映射 → 用户看到的是无用的「未知错误」。

**修复**：`util/LocationError.kt`
- `readableMessage(errorCode, errorInfo = null)` 增加 `errorInfo` 参数（默认值，向后兼容）；
- 新增 `isAuthFailure()`：描述含 `INVALID_USER_SCODE` 或 `auth fail` 时**优先**返回
  「高德鉴权失败：Key / 包名 / 签名 SHA1 三者不匹配。请到高德控制台为本包名补登当前签名 SHA1（更换签名密钥后必须补登）」；
- `ui/point/PointEditScreen.kt` 的 `readableMessage(code)` 同步改为传 `info`。

**真机验证**：调试页现已显示上述可操作提示（不再是「未知错误」）。

### C8（P0）交付包签名与高德登记不匹配 —— 已修【新增，2026-10-13 二次联调】

用户反馈「还是用不了定位功能」。二次真机排查后，确认这是**两套签名并存**造成的，且发现**手机上装的根本不是修复包**。

**排查证据（逐步坐实）**

1. 崩溃堆栈与修复前**逐帧一致**（`ComposerImpl.end`）→ 说明当前运行的没有 C6 修复。
2. 拉取手机上的 `base.apk` 比对：
   | | 手机已装 APK | 本地修复版 |
   | --- | --- | --- |
   | SHA-256 | `2a1a88c6…db7e` | `379d338d…c6653` |
   | 与谁相同 | **= 桌面上的旧包**（Oct-12 00:30） | 本地最新构建 |
   | dex 中 `高德鉴权失败` 串 | ❌ 不存在 | ✅ 存在 |
   → **手机装的是原始未修复包**（多半是误从桌面装回了旧 APK）。
3. 分别实测两套签名的定位能力：
   - 旧包（旧库签名 `d9bd7c66…`，控制台**已登记**）：地图页定位**成功** → `纬度 29.584412，经度 106.521371`，无任何 `auth fail`；
   - 修复包（新库签名 `0f65d51d…`，控制台**未登记**）：`auth fail:INVALID_USER_SCODE#SHA1AndPackage#0f65d51d…:com.example.checkin`。

**修复**：把默认签名切回**控制台已登记的旧密钥库**，一步同时解决两件事：

| 问题 | 原因 | 结果 |
| --- | --- | --- |
| 定位调试页闪退 | 代码缺陷（C6） | ✅ 已在源码修复 |
| 定位无响应 | 签名 SHA1 未登记（C8） | ✅ 切回已登记的旧库签名 |

**附带好处**：与用户手机上现有包**同签名**（`d9bd7c66…`），可直接覆盖安装，**无需卸载、应用数据保留**。

### 关于「定位无响应」——根因是签名，不是代码

真机上分别验证过：**旧签名（控制台已登记）定位成功，新签名（未登记）被拒**。定位链路本身没有代码缺陷；
真正需要的是**让签名 SHA1 与控制台登记保持一致**。本工程已按「已登记的旧库」默认签发（C8），
因此**你无需再去高德控制台做任何操作**。若将来想启用新密钥库，按第七节第 4 项操作即可。
