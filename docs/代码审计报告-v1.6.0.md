## 二、P0 —— 严重缺陷（建议立即修复）

### A1 动态定位调频完全失效，定位间隔永远锁定 30 秒

**定位**
```
app/src/main/java/com/example/checkin/geofence/AMapLocationEngine.kt:192
```
```kotlin
/** 是否为单次定位模式（动态调频仅对连续定位有意义） */
@Volatile
private var onceLocationMode: Boolean = false

fun applyInterval(intervalMs: Long): Boolean {
    if (!onceLocationMode || client == null) return false   // ← 条件写反
    ...
}
```

**根因**
连续定位链路调用 `start(onceLocation = false)`（`GeofenceManager.kt:143~147`），因此 `onceLocationMode == false`。
`!onceLocationMode` → `!false` → `true` → **函数在第一行就 `return false`**，永远走不到后面重建定位客户端的逻辑。
按字段注释的语义，正确条件应为 `onceLocationMode || client == null`。

**影响与范围**
- `LocationIntervalScheduler` 的档位切换（FAR 30s ⇄ NEAR 5s）在**进程内被完整计算但从未下发**，只在日志里输出 `已生效=false`。
- 实际行为：初始化时 `scheduler.currentTier = FAR`，`engine.start(intervalMs = 30_000)`，此后**永远是 30 秒一次定位**。
- 业务后果：README 第三节「功能说明」明确宣传的「动态省电：全部远离时 30 秒定位一次，有接近/进入时提升到 5 秒」**完全不成立**。以 60 km/h 行进，30 秒位移约 500 米，而最大半径仅 500 米（默认 200 米）——存在**整个打卡点被跨过而既不触发进入也不触发离开**的漏报风险。
- 波及模块：`GeofenceManager.adjustInterval` → 全部围栏事件、打卡记录、通知、常驻通知中的频率文案。

**修改方案**
```kotlin
fun applyInterval(intervalMs: Long): Boolean {
    // 单次定位模式或客户端未创建时无需调频
    if (onceLocationMode || client == null) return false
    ...
}
```
**改动量**：1 行。**回归验证**：Debug 页观察回调日志间隔应从恒定 ~30000ms 变为接近阈值时切到 ~5000ms。

### A2 提醒方式（声音 / 震动 / 全屏）设置实际不生效

**定位**
```
app/src/main/java/com/example/checkin/util/PreferencesStore.kt:41~133   （类定义 + 单例）
app/src/main/java/com/example/checkin/ui/MainViewModel.kt:76            （private val preferencesStore = PreferencesStore(application)）
app/src/main/java/com/example/checkin/ui/MainViewModel.kt:192,222       （读取与写入）
app/src/main/java/com/example/checkin/notify/Notifier.kt:189            （val prefs = PreferencesStore.get(context).notifyPreferences）
```

**根因**
`PreferencesStore` 同时承担「DataStore 读写」与「进程级同步缓存」两种职责，而缓存 `notifyPreferences` 是**实例字段**，但存在两条互不相通的实例：

| 使用方 | 取实例方式 | 结果 |
| --- | --- | --- |
| `MainViewModel` | `PreferencesStore(application)` — **新的独立实例** | 读写都落在这个实例的缓存上 |
| `Notifier.post` | `PreferencesStore.get(context)` — **进程单例** | 缓存永远是初始默认值 |

由于没有任何代码对**单例**调用 `readNotifyPreferences()` 或 `setNotifyPreferences()`（已全量检索确认），单例的缓存恒为
`NotifyPreferences(sound = true, vibrate = true, fullScreen = true)`。
因此设置页三个开关改动的效果 **既不会即时生效，也不会在冷启动后生效**，`Notifier.post` 永远按「声音+震动+全屏」全开处理。

**影响与范围**
- 用户在设置页把「全屏提醒」关掉后，锁屏仍会弹出打卡确认页（`setFullScreenIntent`），**这是打扰性最强的行为，用户无法关闭**。
- 关掉声音/震动同样无效。
- 波及：设置页 → 偏好持久化 → 通知构建全链路。属用户可直接感知的功能失效。

**修改方案（推荐）**
1. `MainViewModel` 改用单例：`private val preferencesStore = PreferencesStore.get(application)`；
2. 在 `Notifier.post` 读取前保证缓存已初始化——更稳妥的做法是把缓存提升为**类级（静态）状态**，或在 `CheckinApp.onCreate` 中预热一次：
   ```kotlin
   // CheckinApp.onCreate 内（IO 协程）
   PreferencesStore.get(this).readNotifyPreferences()
   ```
3. 顺手消除 A2 的**结构性成因**（见 D5）：把 `notifyPreferences` 缓存从实例字段改为 `PreferencesStore` 的伴生对象字段，或抽出独立的 `NotificationPrefsCache` 单例对象，从设计上杜绝"多实例缓存不一致"。

**改动量**：1~2 行 + 可选的小重构。**回归验证**：关闭「全屏提醒」→ 触发进入事件 → 锁屏应只出现横幅通知，不再自动弹出确认页。

## 三、P1 —— 高风险（本迭代内必须处理）

### D1 单元测试在当前项目路径下 100% 失败；仓库内记录的修复方案经实测无效

**定位**
```
gradle.properties:3        org.gradle.jvmargs=-Xmx2048m -Dfile.encoding=UTF-8
app/build.gradle.kts       tasks.withType<Test>().configureEach { systemProperty("file.encoding","UTF-8"); jvmArgs("-Dfile.encoding=UTF-8","-Dsun.jnu.encoding=UTF-8") }
README.md「3. 打包」      声称「单元测试必须在纯 ASCII 路径下执行」，并把 encode 修正视为已解决
```

**实测证据（本次审计真实执行）**

| 实验 | 工程路径 | `org.gradle.jvmargs` 是否含 `-Dfile.encoding=UTF-8` | 结果 |
| --- | --- | --- | --- |
| A | `C:\Users\Administrator\Desktop\打卡定位提醒软件` | 是（现状） | **7 个测试类全部失败**，`java.lang.ClassNotFoundException`，通过 0 个 |
| B | `C:\dev\打卡定位提醒软件`（中文） | 是（现状） | 同上，7 失败 0 通过 |
| C | `C:\dev\打卡定位提醒软件`（中文） | **去掉该参数** | **83 个用例全部通过，0 失败** |
| D | `C:\dev\checkin`（ASCII） | 是（现状） | 83 个用例全部通过 |

（实验 C → B 为同一目录、仅改动该一行参数的反向对照，结论可复现。）

**根因**
Windows 平台编码为 GBK(CP936)。`-Dfile.encoding=UTF-8` 只加在 **Gradle daemon** 上，导致 daemon 以 UTF-8 写出测试 worker 的 classpath 参数文件（argfile），而 fork 出的测试 JVM 按平台默认编码（GBK）读取该文件 → 中文路径被写坏 → 类加载器找不到任何测试类。
`app/build.gradle.kts` 里给 **Test 任务**加的 `file.encoding / sun.jnu.encoding` 只在 worker JVM 生效，**无法修复 daemon 侧的编码不对称**，所以那段"修复"实际上从未起作用（README 的说明也随之失真）。

**影响与范围**
- 这是本项目当前**最卡脖子的工程问题**：在不改动路径或参数的前提下，任何代码改动都**无法回归验证**；CI 若沿用此配置会全红或长期"跳过测试"。
- 影响：全部 9,791 行主源码的改动安全性、83 个既有用例的全部价值（状态机、去重器、地理计算、隐私合规、实体约束均已写好但形同虚设）。

**修改方案（二选一，推荐方案 1）**
1. **把工程移到纯 ASCII 路径**（如 `D:\projects\checkin`），并同步修正 `local.properties` 的 `sdk.dir`。同时删除 `app/build.gradle.kts` 底部的「单元测试 JVM 编码修正」段落（无效且误导），修正 `README.md` 的对应说明。
2. **保留中文路径**：`gradle.properties` 改为 `org.gradle.jvmargs=-Xmx2048m`（去掉 `-Dfile.encoding=UTF-8`；源码文件本身已是 UTF-8，且 `kotlin.code.style=official` 不受影响），并同样删除 `app/build.gradle.kts` 中那段无效配置。
   ⚠️ 需确认保留中文路径时构建产物中的中文资源（`strings.xml` 已是 UTF-8 且 AAPT 显式按 UTF-8 读取）不受影响——建议方案 2 落地后执行一次 `assembleRelease` 并安装验证。

**优先级理由**：这是所有后续修复的**前置条件**——没有可运行的测试，修复 A1/A2 只能靠人工真机验证。

### D2 `fallbackToDestructiveMigration()`：任何一次数据库版本升级都会清空用户全部数据

**定位**
```
app/src/main/java/com/example/checkin/data/local/CheckinDatabase.kt:44~52
```
```kotlin
/**
 * v1 -> v2 表结构发生了重命名（...），
 * v1 属于开发阶段结构且无正式数据，因此采用破坏性迁移。
 * ★ 若线上已发布 v1，请改为提供显式 Migration，切勿保留此调用。
 */
.fallbackToDestructiveMigration()
```

**风险**
- 当前 `version = 2`，且 `app/schemas/` 下仅有 `1.json` 与 `2.json`，**没有任何 `Migration` 实现**。
- v1.6.0（DB v2）**已经打包交付**（`定位打卡-v1.6.0-release.apk` 存在于工程根目录），即已存在真实用户数据（打卡点坐标、全部打卡历史）。
- 下一次表结构调整（哪怕只加一列）若忘记写 Migration，Room 会**静默删除整库重建**——用户的全部打卡点与打卡记录无提示丢失，且无备份可恢复。
- 注释里写的"若线上已发布 v1 请改"这个前置条件**现在已经成立**，但代码没有随之调整。

**修改方案**
1. **立即**把 `fallbackToDestructiveMigration()` 替换为仅针对降级场景的宽松策略：
   ```kotlin
   .fallbackToDestructiveMigrationOnDowngrade()
   ```
   这样"升级"路径一旦缺 Migration 会**直接崩溃并暴露问题**（而不是静默清库），"降级"（用户装回旧版）仍可自动恢复。
2. 为下一次版本升级（v2 → v3）预置显式 `Migration`，并在 `databaseBuilder` 上 `addMigrations(MIGRATION_2_3)`。
3. 建议引入 `room-ktx` 的自动迁移能力（`@AutoMigration`）：开启 `ksp { arg("room.generateKotlin","true") }` 后，纯加列/加表类变更可由 Room 自动生成迁移，配合显式 `@AutoMigration(from = 2, to = 3)`，大幅降低人工遗漏风险。

**改动量**：1 行（可立即止血）+ 后续每次改表时约 5~15 行。**影响范围**：全部持久化数据。

### B1 `allowBackup="true"`：打卡点坐标与全部打卡历史会被云备份（隐私风险）

**定位**
```
app/src/main/AndroidManifest.xml:53          android:allowBackup="true"
app/src/main/res/xml/backup_rules.xml:4~8    include database/checkin.db；include sharedpref 全部
app/src/main/res/xml/data_extraction_rules.xml:5~14  云备份与设备迁移均 include checkin.db 与 sharedpref 全部
```

**风险**
- 本应用的数据核心是**精确地理位置**：`checkin_point`（打卡点经纬度）与 `checkin_record`（每次打卡的实时经纬度与时间）。
- `allowBackup=true` 且规则显式 `include` 了 `checkin.db`，意味着这些位置数据会随 Android 自动备份上传到用户设备厂商/Google 云盘，并在换机时自动迁移。
- 应用自身的隐私弹窗（`PrivacyConsentDialog`）明确向用户承诺："位置信息仅在设备本地与打卡点坐标做距离比较，**不会上传到我们的服务器**"。虽然"我们的服务器"与"系统云备份"是两回事，但从用户认知与监管口径看，**位置数据在没有明确告知的情况下离开设备**存在合规瑕疵。
- 规则里 `exclude domain="sharedpref" path="fence_state.xml"` 排除的是一个**并不存在**的偏好文件（实际偏好是 `checkin_prefs` DataStore 与 `privacy_consent` SharedPreferences），说明这份规则是从模板复制的、未经核对。

**修改方案（三选一）**
1. **推荐**：`android:allowBackup="false"` —— 位置类应用最简单、最安全的合规姿势；同时删除 `backup_rules.xml` / `data_extraction_rules.xml` 两个引用。
2. 保留备份但**仅备份偏好、不备份位置数据**：
   ```xml
   <full-backup-content>
       <include domain="sharedpref" path="." />
       <exclude domain="database" path="checkin.db" />
   </full-backup-content>
   ```
   并在隐私弹窗文案中补充"允许系统备份偏好设置"的说明。
3. 若坚持备份数据库：需在隐私声明中显式告知，并考虑为 DB 增加加密（SQLCipher），成本最高。

**影响范围**：隐私合规 + 用户数据可携带性。**改动量**：1~4 行。

- 同一把密钥同时用于 `debug` 与 `release`（`app/build.gradle.kts` 的 `debug` 块），进一步扩大了密钥的使用面与泄露渠道。

**修改方案**
1. **正式发布必须生成新密钥库与强口令**（≥16 位随机），并替换现有 `checkin-release.jks`；

3. `app/build.gradle.kts` 中的签名口令改为**优先读环境变量 / Gradle 属性**，`keystore.properties` 仅作本地开发兜底：
   ```kotlin
   val storePassword = System.getenv("CHECKIN_STORE_PASSWORD")
       ?: keystoreProperties.getProperty("storePassword")
   ```
4. 密钥库与口令交接走密码管理器（KeePass/1Password/Vault），不落文档。

**影响范围**：发布链路安全、应用身份可信度。**注意**：更换密钥后已发布 APK 无法被覆盖安装，需先确认目标用户是否可接受卸载重装；若不能，则本项仅执行第 2~4 步。

## 四、P2 —— 中等风险

### A3 唤醒锁 1 小时后静默失效，锁屏定位可能停摆

**定位**：`CheckinForegroundService.kt:143~156`（`acquire`）、`:306`（`WAKE_LOCK_TIMEOUT_MS = 60 * 60 * 1000L`）
**问题**：`PARTIAL_WAKE_LOCK` 带 1 小时超时作为兜底（设计正确），但**唯一获取点是 `onStartCommand`**，且 `acquirePartialWakeLock()` 在 `isHeld == true` 时直接返回。服务长时间常驻时，只要 1 小时内没有新的 `onStartCommand`（看活闹钟在 Doze 深度休眠/被 ROM 拦截时可能被抑制），唤醒锁到期后**无人续期**，CPU 可进入休眠，锁屏后的定位回调被推迟或停摆——正是该锁要解决的问题本身。
**修改方案**：在定位回调链路中续期，例如在 `GeofenceManager.handleLocation` 末尾通过回调通知服务检查：
```kotlin
// CheckinForegroundService
geofenceManager.onHeartbeat = { 
    if (wakeLock?.isHeld != true) acquirePartialWakeLock() 
}
```
或在 `CheckinForegroundService.onStartCommand` 之外，由 `ServiceWatchdog` 的每次触发顺带续期（`WatchdogReceiver` → `CheckinForegroundService.start()` 已能走 `onStartCommand`，需确认调用链稳定）。建议采用前者，语义最直接。

### A4 离开事件被写成"待确认打卡记录"，用户打卡时会把它就地改写

**定位**：`GeofenceManager.kt:228~240`（EXIT 事件同样 `source = AUTO_CONFIRMED`）、`CheckinRecordDao.kt:54~61`（`latestPendingForPoint` 仅按 `source` 过滤）、`CheckinRecordRepository.kt:61~93`
**问题**：`latestPendingForPoint` 的 SQL 只过滤 `source = 'AUTO_CONFIRMED'`，**不区分 `is_enter`**。因此：
1. 用户离开打卡范围 → 生成一条 `is_enter = 0` 的 AUTO_CONFIRMED 记录；
2. 用户点"立即打卡"（或点击离开提醒进入确认页打卡）→ `checkIn()` 取到**那条离开记录**，就地改写成 `MANUAL`，并把 `time` 覆盖为当前时间；
3. 结果：**离开事件被吞掉**（历史里再也看不到"离开"），且该条记录的语义从"离开事件"变成"手动打卡"，进出记录不再配对。
**修改方案**
- `latestPendingForPoint` 增加 `AND is_enter = 1`（SQL 层过滤，不做应用层过滤）；
- 或为 EXIT 事件引入独立的 `CheckInSource.FENCE_EXIT`，彻底与"待确认打卡"解耦（推荐，语义更清晰）。
**补充**：`CheckinRecord.isEnter` 为 `Boolean?`，`false` 与 `null` 语义不同（离开 vs 手动），当前 `source = AUTO_CONFIRMED` 同时承载两种事件，建议一并梳理。

### A7 地图销毁后 Marker/Circle 引用未清空，TextureMapView 未从容器移除

**定位**：`PointEditScreen.kt:345~366`（生命周期转发）、`:380~450`（AndroidView update）
**问题**：`ON_DESTROY` 分支把 `mapView = null; aMap = null`，但 `marker` / `circle` 仍持有已销毁地图上的图形对象引用；同时 `AndroidView` 的 factory 返回的 `FrameLayout` 里已 `addView(TextureMapView)`，`onDestroy` 时**未 `removeView`**。Activity 重建（屏幕旋转、深色模式切换、字体大小变更）时 `AndroidView` 容器可能复用旧容器，`update` 分支因 `mapView == null` 会**再 `addView` 一个新的 TextureMapView**，导致"重复添加 View"或地图不渲染/内存泄漏。
**修改方案**
```kotlin
Lifecycle.Event.ON_DESTROY -> {
    locationEngine.stop()
    marker = null
    circle = null
    mapView?.let { container.removeView(it); it.onDestroy() }   // 需在 update 中持有 container 引用
    mapView = null
    aMap = null
}
```
并在 `DisposableEffect.onDispose` 中兜底释放。

### B2 `BootCompletedReceiver` 无需 `exported="true"`

**定位**：`AndroidManifest.xml:151~165`
**问题**：该 Receiver 只接收系统广播（`BOOT_COMPLETED` 等）。按 Android 官方语义，`android:exported="false"` 的组件**仍可接收系统广播与同 UID 广播**，因此 `exported="true"` 属于**不必要的对外暴露**。当前任意第三方应用都可以发送同名 action 的显式/隐式广播，触发本应用读取数据库并 `startForegroundService` —— 可被用于**耗电骚扰 / 拒绝服务**（反复拉起前台定位服务）。
**修改方案**：改为 `android:exported="false"`（保留全部 `intent-filter`），并在真机验证开机自恢复仍正常。

### B3 全屏提醒在 Android 14（targetSdk 34）上静默降级

**定位**：`Notifier.kt:228~230`（`setFullScreenIntent(contentIntent, true)`）、`AndroidManifest.xml`（未声明 `USE_FULL_SCREEN_INTENT`）
**问题**：本应用 `targetSdk = 34`。自 Android 14 起，`USE_FULL_SCREEN_INTENT` 仅对**闹钟/通话类**应用默认授予，其余应用该权限默认**被撤销**；未持有时系统会把全屏 Intent **静默降级为普通横幅通知**。本应用清单里连该权限都未声明，因此"锁屏直接弹出打卡确认页"这一核心体验在 Android 14 设备上**不可用**，且用户与开发都无从感知。
**修改方案**
1. 清单声明：`<uses-permission android:name="android.permission.USE_FULL_SCREEN_INTENT" />`；
2. 运行时检测并在需要时引导用户授权（API 34+）：
```kotlin
val nm = context.getSystemService(NotificationManager::class.java)
if (Build.VERSION.SDK_INT >= 34 && !nm.canUseFullScreenIntent()) {
    // 引导至 Settings.ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT
}
```
3. 在 `SelfCheckRunner` 中新增一项自检（该项目前无覆盖），并在 `SettingsScreen` 中给出手动授权入口。

### C1 `SimpleDateFormat` 在 Composable 内每次调用新建

**定位**：`RecordsScreen.kt:47~48`（`formatTime` 每次 `new SimpleDateFormat`）→ 在 `RecordCard`（`:158`）内被调用；`CheckinConfirmScreen.kt:362` 同理；`DebugViewModel.kt:216` 每次追加日志也新建。
**问题**：`RecordCard` 每行每次重组都构造一个新的 `SimpleDateFormat`，`LazyColumn` 滚动时高频对象分配与 `Locale` 查表，属典型渲染期开销。
**修改方案**：改用线程安全且可静态复用的 `java.time`：
```kotlin
private val TIME_FMT = DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss", Locale.CHINA)
private fun formatTime(ts: Long): String =
    Instant.ofEpochMilli(ts).atZone(ZoneId.systemDefault()).format(TIME_FMT)
```
（minSdk 26，`java.time` 可直接使用，无需 desugaring。）

### C2 服务状态 2 秒轮询常驻，与注释不一致且耗电

**定位**：`MainViewModel.kt:199~204`（`while (true) { ...; delay(SERVICE_STATE_POLL_MS) }`）、`:377~378`
**问题**：①注释写"**每秒**刷新一次"，常量值却是 `2_000L`，实现与文档不一致；②该轮询位于 `init {}` 中无条件 `launch`，**不受 `stateIn(WhileSubscribed)` 控制**，只要 ViewModel 存活（即使 App 退到后台、设置页从未打开）就持续唤醒；每 2 秒一次唤醒对"本身就是耗电敏感型应用"的项目不合适。
**修改方案**：改用可订阅驱动的 Flow（如把服务状态抽成 Flow 并用 `stateIn(SharingStarted.WhileSubscribed(5_000))`），或把周期放宽到 5~10 秒，并修正注释。

### D3 lint 被彻底关闭，放弃静态质量门禁

**定位**：`app/build.gradle.kts` → `lint { abortOnError = false; checkReleaseBuilds = false }`
**问题**：两项同时关闭等于**完全不做静态检查**（`checkReleaseBuilds = false` 时 release 构建根本不跑 lint）。这正是 A1 这类"条件写反"缺陷本可被规则兜住的场景（如 `MissingPermission`、`WrongConstant`、未使用资源/依赖等）。
**修改方案**：分两步恢复门禁，避免一次性红海：
```kotlin
lint {
    checkReleaseBuilds = true
    abortOnError = false
    baseline = file("lint-baseline.xml")   // 先生成基线，只拦截新增问题
    warningsAsErrors = false
}
```
执行一次 `./gradlew lintRelease` 生成基线后，把 `abortOnError` 改为默认 `true`。

### C3 状态机单次定位触发 O(2N) 次 StateFlow 发射

**定位**：`FenceStateMachine.kt:162~208`
**问题**：`evaluate()` 对每个打卡点在多个分支里各自调用一次 `_states.update { map + (id to ...) }`，每次 `update` 都**拷贝整个 Map 并发射一次 StateFlow**。N 个点时单次定位最多产生 2N 次发射，UI 侧 `combine(FenceMonitor.states, ...)` 与 `LazyColumn` 会跟着重组 N 次。当前点位数量少（典型 <20）时影响可忽略，但属明确的放大效应。
**修改方案**：在 `evaluate()` 内累积到局部 `LinkedHashMap`，**循环结束后一次性 `_states.value = newMap`**，单次定位只发射一次。
**附带**：`GeofenceManager.adjustInterval()` 中 `activePoints.minByOrNull { stateMachine.states.value[...] }` 在 lambda 内重复读 `StateFlow.value`，建议先取一次快照。

### C4 调频实现为"停止 → 重建定位客户端 → 重启"，抖动会打断定位流

**定位**：`AMapLocationEngine.kt:191~206`、`LocationIntervalScheduler.kt:126`（节流 20 秒）
**问题**：高德 SDK 不支持运行时改间隔，必须重建客户端（官方推荐做法，本实现正确）。但修好 A1 后需注意：每次档位切换都要 `stopLocation + onDestroy + new AMapLocationClient + startLocation`，且**这个过程发生在 `handleLocation` 回调内部**（`GeofenceManager.handleLocation` → `adjustInterval` → `applyInterval` → `start` → `stop`），即在监听器执行期间销毁并重建自身客户端，存在回调期间状态不一致的隐患。若用户正好在阈值附近移动，档位反复切换会持续打断定位流。
**修改方案**
1. 把调频动作**投递到主线程消息队列尾部**（`Handler(Looper.getMainLooper()).post { ... }`），避免在回调栈内销毁客户端；
2. 评估把节流从 20 秒放宽到 60 秒，或引入"离开 NEAR 档后延迟 N 秒才降频"的双阈值策略；
3. 记录 `applyInterval` 的重建次数并在 Debug 页展示，便于真机评估抖动。

## 七、值得肯定的设计（不在修改范围）

以下实现质量较高，建议在后续重构中保持，勿因改动而破坏：

- `FenceStateMachine` 做成**纯逻辑、无 Context、无 IO**，因此 30 个用例可在 JVM 上完整覆盖状态流转、防抖、容差与边界（`恰好在半径上判定为进入`）。
- 定位精度作为**有上限的容差**参与判定（`MAX_TOLERANCE_METERS = 50f`），既不因漂移抖动也不因精度极差而误判。
- 高德 `GeoFenceClient` **只作日志与核对**，权威判定交给自研状态机，规避了"围栏静默不回调导致漏报"——这是同类应用中很常见的坑。
- 通知去重做**两层独立防线**（状态机本身不重复产出事件 + `NotificationDeduper`），注释明确说明是"即使状态机将来被改坏也不会轰炸用户"。
- 隐私合规链路严谨：`PrivacyConsentStore` 用 SharedPreferences 而非 DataStore，并在注释中记录了"曾因异步读取导致定位错误码 27"的真实踩坑；`updatePrivacyShow/Agree` 在实例化任何 SDK 客户端之前调用。
- 厂商 ROM 适配有克制：能查的（电池优化白名单、通知、定位权限）给真实状态，查不到的（自启动）**明确标为 `manualOnly` 而不谎报通过**。
- 高德隐私接口对地图侧采用**反射 + 存在性判断**，避免编译期绑定到某个版本。
- 协程作用域管理无 `GlobalScope`；`GeofenceManager` 明确注释了"`scope` 一旦 cancel 就永久失效，必须在每次 start 重建"——这是一个非常容易被忽略的坑。
- 错误码到中文文案的映射覆盖了 0~31 全区间，且 `from()` 保留原始 errorCode/errorInfo 便于排查。
